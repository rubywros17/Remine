# Remine 서비스 기획서 (spec)

> 서비스명: **Remine** (리마인)
> 작성일: 2026-10-07 · 상태: MVP 기획 단계

### 이름의 의미
- **re** (다시) + **mine** (캐내다 / 내 것)
- "묵혀둔 캡처를 다시 캐내서, 다시 내 것으로" — 발음이 *remind*와 거의 같아 리마인드 서비스라는 점도 함께 전달된다.
- 참고: 동명의 해외 서비스(부동산 플랫폼, 메모 앱)와 유사 이름 앱(Remini)이 있어, 정식 출시 시 스토어 부제·상표 확인 필요.

### 브랜드 컬러·디자인
색·폰트·모서리·모션 등 앱 디자인 기준은 [design.md](design.md)가 정본이다(셀라돈 `#7DC4CE`가 브랜드 색, 레몬 `#EDE7B3`은 관심사·선택 강조).

---

## 1. 한 줄 소개

캡처해두고 잊어버린 스크린샷을 자동으로 분류해 예쁘게 보여주고, 자주 캡처했던 **잊은 관심사**를 먼저 꺼내서 알려주는 앱.

## 2. 문제 정의

- 사람들은 나중에 보려고 스크린샷을 저장하지만, 앨범에 쌓이기만 하고 다시 보지 않는다.
- 그 안에는 사고 싶었던 상품, 보고 싶었던 영화·드라마, 가보고 싶은 장소 같은 **본인의 관심사**가 담겨 있다.
- 기존 스크린샷 정리 앱은 대부분 "검색하면 찾아주는" 수동적인 도구에 머문다.

## 3. 차별점

| 기존 앱 | 이 서비스 |
|---|---|
| 내가 검색해야 찾아줌 | 서비스가 **먼저 말 걸어줌** |
| 분류·검색 중심 | 분류 + **관심사 패턴 감지 + 리마인드** |
| iOS·Pixel 위주 | **갤럭시(안드로이드) 우선** — Pixel Screenshots는 Pixel 전용 |

## 4. 타깃

- 1차: 스크린샷을 많이 찍는 한국 갤럭시 사용자 (개발자 본인 포함)
- 2차: iOS 사용자 (MVP 이후 확장)

---

## 5. MVP 범위

### 목표
> 갤럭시 앨범의 스크린샷을 자동으로 카테고리별로 예쁘게 보여주고, 자주 캡처한 관심사를 주 1회 알려준다.

### ✅ MVP 기능

**F-01. 스크린샷 불러오기**
- 앨범의 `Screenshots` 폴더만 읽는다.
- 첫 실행 시 최근 N장(기본 300장)만 분석해 첫 경험을 빠르게 한다.
- 서버는 analyze 요청 하나에 **최대 20장**(`remine.analyze.max-batch-size`)만 받으므로 앱이 **20장씩 나눠** 순차 요청한다. 초과하면 400이다.
  (분류 호출이 순차이고 무료 등급 속도 제한 때문에 호출 간격을 두어, 20장 요청은 최소 약 1.5분이 걸릴 수 있다. 비동기·병렬 분석은 미정 사항.)
- 이후 새로 추가된 스크린샷만 증분 분석한다.

**F-02. 자동 분류 + 태그**
- 기기 안에서 OCR로 텍스트 추출 (ML Kit, 한국어).
- **기기 읽기·OCR 구현(`feat/gallery-ocr`)**
  - 읽기: `photo_manager`로 `Screenshots` 앨범 최근 **300장**(촬영 최신순). 같은 이름의 앨범이 여럿이면 경로가 `DCIM/Screenshots`인 것을 기본 소스로 쓰고, 없으면 이름이 Screenshots/스크린샷인 앨범 중 사진이 가장 많은 것으로 대체한다. 다른 같은 이름 앨범은 자동으로 합치지 않고 측정 화면 칩에서만 고른다(이름이 겹치면 칩에 경로가 붙는다). 권한은 Android 13+ `READ_MEDIA_IMAGES`, 14+ "일부만 허용"(`READ_MEDIA_VISUAL_USER_SELECTED`)을 처리한다. 일부 허용이면 고른 사진만 보이고 **새 스크린샷은 자동으로 가져올 수 없다**는 안내와 [다시 고르기]를 보여 준다. 거부면 안내 화면에서 [권한 허용]·[설정 열기].
  - OCR: ML Kit **한국어 번들 모델**(첫 실행 다운로드 없이 오프라인). OCR 입력은 **앱 캐시 폴더 안 임시 복사본**이고, 끝나면 그 복사본만 지운다(사진 원본 경로는 지우지 않는다). 원문은 로그에 남기지 않는다.
  - 결과 보관: 앱 **로컬 SQLite**(`ocr_result`: asset id, 파일명, 수정시각, 텍스트, 글자 수, OCR 시각, 엔진). 사진이 바뀌지 않았으면 재처리하지 않는다. 안드로이드 자동 백업은 꺼서(`allowBackup=false`) OCR 원문이 Google 계정으로 올라가지 않는다.
  - 이 단계에는 **네트워크 호출이 없다**(서버 전송은 3주차). 테스트가 HTTP 계열 의존성·호출이 없음을 확인한다.
  - 디버그 빌드 전용 "OCR 측정" 화면에서 고른 사진의 파일명·글자 수·텍스트를 JSON으로 내보내 ML Kit 기준으로 재측정한다([experiment/README.md](../experiment/README.md)). 릴리스 빌드에는 들어가지 않는다.
- **분류 입력은 하이브리드**다. 기기에서 OCR 글자 수(공백 제외)를 세어 기준값과 비교한다.
  - **기준값 이상(기본 150자)**: OCR **텍스트만** 서버로 전송한다.
  - **기준값 미만**: 텍스트와 함께 **긴 변 1024px로 축소한 이미지**를 보낸다. 단, 사용자가 **이미지 분석에 동의한 경우에만**이다.
    동의하지 않았으면 텍스트만 보내며, 이 경우 짧은 캡처의 정확도가 낮아진다(실험: 50자 미만 텍스트만 13.3%, 이미지 포함 80.0%).
  - 기준값은 하드코딩하지 않고 **설정**으로 둔다(서버 설정 `remine.llm.image-threshold-chars`, 기본 150, 앱은 `GET /api/config`의 `imageThresholdChars`로 받아 사용).
  - **이미지 형식·크기**: JPEG만(서버가 매직 바이트로 확인), 장당 최대 `imageMaxBytes`(기본 1MB), 긴 변 `imageMaxLongSide`(기본 1024px) 이하로 줄여 보낸다. 더 크면 서버가 한 번 더 줄이며, 서버는 항상 다시 인코딩하므로 EXIF·GPS 같은 메타데이터가 남지 않는다.
  - **서버가 이미지를 쓰는 조건**은 분류기 한 곳에서 정한다: OCR이 비어 있거나 기준값 미만이고, `[전화번호]` 표시가 없을 때만 쓴다. 그 밖(기준값 이상, 마스킹 표시 있음, 이미 분석된 캡처)에 이미지가 와도 오류 없이 **무시**하며 디코딩도 하지 않는다(로그에는 사유 코드와 건수만).
  - **빈 OCR + 이미지**: 분류기로 보낸다(이미지로 분류). **빈 OCR + 이미지 없음**: LLM 없이 `ETC`.
  - 기기 안에서 먼저 **민감 정보 필터**를 거친다([개인정보 원칙](#개인정보-원칙) 참고).
    - **강한 민감 정보**(주민등록번호, 카드·계좌번호, 인증번호(OTP), 비밀번호): 서버로 보내지 않고 기기에서 `ETC`로 분류한다. 텍스트·이미지 모두 기기를 떠나지 않는다.
    - **전화번호**: 차단하지 않는다. OCR 텍스트에서 `[전화번호]`로 가린 뒤 **텍스트만** 보내고 이미지는 보내지 않는다. 서버도 `[전화번호]` 표시가 있으면 이미지가 와도 쓰지 않는다(이중 방어).
    - **은행·증권·메신저 앱 캡처**: 서버로 보내지 않고 기기에서 앱 기준으로 바로 분류한다(메신저 → `CHAT`, 은행·증권 → `ETC`).
    - **Remine 자기 화면 캡처**: 분류 대상이 아니라 OCR·전송·목록에서 모두 뺀다. 갤럭시는 우리 앱 화면 캡처 파일명에 앱 이름을 붙이지 않아서, "파일명에 앱 이름이 없음 + 촬영 시각이 앱이 앞에 있던 구간(resumed~paused, 앞뒤 5초) 안"이면 자기 캡처로 본다. 구간은 기기에만 최근 90일 보관한다. 구간 기록이 생기기 전 캡처는 설치 ~ 이 규칙이 들어간 업데이트 시각을 한 번 정해 그 기간의 이름 없는 캡처만 빼고, 이미 서버에 보낸 것은 `POST /api/screenshots/forget`으로 지운다.
- LLM(`gemini-3.5-flash-lite`, temperature 1.0)이 카테고리·태그·한 줄 요약을 생성한다. 근거와 한계는 `experiment/SUMMARY.md`.
  - 요약은 핵심 대상 + 내용의 20자 안팎 명사구다(마침표·"-다" 금지, "화면/캡처/스마트폰" 금지). 운영 프롬프트 v3 = v1 카테고리 정의 + 이 요약 형식.
  - 서버는 요청 안의 캡처를 텍스트만 10장, 이미지 포함 5장씩 한 LLM 요청으로 묶는다(`remine.llm.batch.*`, 1이면 장당 1요청). 응답에서 빠지거나 해석 못 한 장만 단건으로 다시 보내고, 호출 자체가 실패하면 묶음 전체를 실패로 둔다(앱이 다시 보낸다).
- 기본 카테고리 (고정). 코드 값(enum) → 앱 표시 라벨:

  | 코드 값 | 앱 표시 라벨 | 비고 |
  |---|---|---|
  | `SHOPPING` | 쇼핑 | 상품, 가격, 구매, 장바구니, 배송. 가격·할인·장바구니·배송이 보이면 대개 SHOPPING |
  | `ENTERTAINMENT` | 문화생활 | 영화·드라마·OTT·연극·뮤지컬·공연·전시·책·음악 등 보고 싶은 작품·콘텐츠 |
  | `PLACE` | 맛집/장소 | 맛집·카페·팝업스토어·여행지 등 "가보고 싶은 곳" (운영 기간이 있어도 장소가 핵심이면 PLACE). 주소·영업시간·메뉴·위치가 보이면 대개 PLACE |
  | `INFO` | 정보/꿀팁 | 뉴스·꿀팁·방법 설명, 레시피·DIY·코디처럼 "알아두거나 따라 해보려는 것" |
  | `CHAT` | 대화 | 메신저·댓글 대화. 메신저 앱 캡처는 기기에서 바로 `CHAT`으로 분류한다(서버로 보내지 않음, 일반 캡처처럼 노출) |
  | `SCHEDULE` | 일정/예약 | 작품 자체가 아니라 날짜·예약·티켓 오픈이 핵심이면 SCHEDULE. 특정 날짜·시간, 예매 오픈, 예약 완료가 핵심이면 SCHEDULE |
  | `ETC` | 기타 | |

**F-03. 정리 화면**
- 홈: 카테고리 카드 + 썸네일 미리보기
- 카테고리 상세: 이미지 그리드 + 태그 칩 필터
- 스크린샷 상세: 원본 이미지 + AI 요약 + 태그
- **"분석 제외" 필터**: 서버 분석을 거치지 않고 기기에서 분류된 캡처(강한 민감 정보, 은행·증권 앱)를 모아 본다.
  이 캡처들은 정리 화면에서 **기본 숨김**이다. 메신저 앱 캡처(`CHAT`)는 일반 캡처처럼 노출한다.
- 홈의 카테고리별 개수·썸네일은 서버 집계와 기기 내 분류 결과를 합쳐 보여준다.

**F-04. 잊은 관심사 알림**
- 서버가 태그 빈도를 집계해 관심사를 감지한다.
  - 규칙: 기기별로 최근 14일(`taken_at`) 안에 같은 태그 3회 이상. 기준값은 설정(`remine.interest.window-days`·`min-count`).
  - 태그는 저장 전에 정리한다: 화면 문구(장바구니·무료배송 등)와 카테고리명(쇼핑·정보 등)은 불용어로 빼고(목록은 `application.yaml`의 `remine.tags.stopwords` 한 곳), `#`·공백·대소문자를 무시한 키로 "니트 가디건"과 "니트가디건"을 같은 태그로 센다. 표시 이름은 처음 들어온 표기.
  - 대표 카테고리는 그 캡처들의 현재 `category`(사용자 수정 반영) 최빈값, 동점이면 가장 최근 캡처의 값.
  - 앱은 휴지통에 넣은 캡처를 횟수에서 빼고, 기준 아래로 내려가면 그 관심사를 숨긴다(응답의 `recent`에 있는 캡처만 알 수 있는 한계).
- 앱 화면
  - 관심사 카드(관심사 탭·홈)·상세의 "같은 관심사"·관심사 알림을 누르면 **태그 모아보기**: "#태그" 제목 아래 "최근 2주 N장 · 전체 M장", 그리드는 "최근 2주" → "그 전" 순. 상세의 좌우 넘기기는 이 목록 안에서만.
  - 관심사 탭에 들어올 때마다 먼저 **머릿속 캡처 지도**(약 3초 동안 그려짐): 뇌 윤곽 → 채움 → 소뇌·뇌간 → 주름 → 관심사 원(상위 7개, 많이 캡처할수록 큼) → `linkedTags` 연결선 → 잊은 관심사(마지막 캡처 7일 이상)가 레몬색으로 깨어남. 다 그려져도 지도 그대로이고, 아래 [목록 보기]나 화면을 누르면 목록. 애니메이션 줄이기면 완성된 지도를 바로 보여 준다. 관심사가 없으면 바로 빈 상태.
- 주간 집계: 주 1회(월 10시, Asia/Seoul) 기기마다 관심사 1순위를 `interest_alert`에 `PENDING`으로 저장한다.
  - 멱등: 기기당 한 주 1건(`device_id + week_start` unique). 같은 주에 다시 돌아도 결과가 같다.
  - 쿨다운: 최근 28일 안에 후보였던 태그는 다시 고르지 않고 다음 순위를 본다. 횟수가 늘어도 예외 없음(주 1건이라 같은 태그 반복보다 다른 관심사에 자리를 준다). 필요해지면 저장해 둔 `capture_count`와 비교해 "2배 이상이면 무시"를 추가할 수 있다.
- 푸시 발송 (FCM): 발송 cron(`remine.push.send-cron`, 기본 10~21시 30분마다, Asia/Seoul)이 **이번 주** `PENDING`을 보낸다.
  - 문구(해요체): "요즘 '신발'을 3번 캡처했어요. 다시 볼까요?" (을/를은 받침으로 고름). data는 `{type: interest, tag, category}`뿐 — OCR 원문·요약 없음.
  - 성공 → `SENT`(`sent_at`). 실패 → `PENDING` 그대로, 다음 실행에 재시도. 지난주 이전 `PENDING`은 발송 실행이 `EXPIRED`로 정리(지나간 관심사는 보내지 않음).
  - 무효 토큰: FCM이 `UNREGISTERED`·`SENDER_ID_MISMATCH`라고 할 때만 기기 토큰을 지운다(기기 행은 유지). `INVALID_ARGUMENT`는 메시지 문제일 수 있어 재시도. 토큰이 없는 기기에는 보내지 않는다.
  - Firebase 키(`remine.fcm.credentials-file`)가 없으면 푸시만 꺼지고(기동 때 경고 1번) 나머지는 정상.
  - 앱: 알림을 누르면 그 카테고리 화면을 태그로 거른 상태로 연다. 앱이 앞에 있을 때 온 알림은 띄우지 않는다(FCM 기본 동작).
  - 알림 받기는 사용자가 고른다(로컬 저장, 아직 안 고름/켬/끔). **서버에 토큰이 있는 건 켰을 때뿐**: 켜면 토큰 PUT, 끄면 DELETE, 앱 시작 때 설정에 맞춰 다시 맞춘다.
  - 첫 분석 완료 화면에서 [홈으로]를 누르면 아직 안 골랐을 때 한 번 전체 화면 안내 → [알림 받기]면 시스템 권한 창(허용이면 켬), [나중에]·뒤로 가기면 끔. 설정의 스위치로 언제든 바꾼다(영구 거부면 휴대폰 설정 안내 + [설정 열기]).

**F-05. 사용자 카테고리 수정**
- AI가 분류한 카테고리가 틀리면 사용자가 스크린샷 상세 화면에서 **7개 기본 카테고리 중 하나로 직접 바꾼다.**
- 수정한 값은 AI 분류보다 우선하며 이후 재분석이 덮어쓰지 않는다. 서버에는 모델이 처음 낸 값 `auto_category`(분석 시 한 번 저장, 이후 불변)와 현재 값 `category`, 출처 `category_source`(**AUTO** / **USER**)를 저장한다.
- **같은 값으로 "수정"해도 `USER`가 된다**(= 사용자 확인). 틀렸다고 고친 것(`corrected`)과 맞다고 확인한 것(`confirmed`)을 구분해야 정확도를 잴 수 있고, 확인된 값도 재분석에서 보호된다.
- **보호 규칙은 저장 로직(엔티티)에 있다**: `category`·`auto_category`는 분석 반영(`applyAnalysis`)과 사용자 수정(`changeCategoryByUser`)으로만 바뀌고, `USER`인 값은 어떤 재분석 경로도 덮어쓰지 못한다(요약은 카테고리와 독립으로 갱신). 분석되지 않은 캡처는 수정할 수 없다.
- 홈의 카테고리별 개수·대표 태그·썸네일과 목록 필터는 수정된 `category`를 기준으로 집계하며 수정 즉시 반영된다. 태그는 그대로 유지된다.
- 정정 데이터는 이후 분류 품질 평가용 라벨로 쓸 수 있다([실사용 정확도 측정](#실사용-정확도-측정-f-05) 참고).
- 새 카테고리를 만드는 **사용자 정의 카테고리**와는 별개이며 MVP 이후다.

**F-06. 사진 정리(휴지통)** — 앱 내 휴지통(이번 단계) / 기기·서버 삭제(3주차 이후)
- 상세 화면에서 캡처를 **위로 던져** 휴지통으로 옮긴다(보이는 메뉴는 없고, 화면 읽기 동작 "휴지통으로 옮기기"로도 가능). 되돌리기는 몇 초(4초) 동안 스낵바로 제공한다. 모션·제스처 명세는 [design.md](design.md)의 상세 화면.
- **지금 구현 범위(앱 내 휴지통)**: 앱의 Repository에만 `trash`/`restore` 개념이 있다. 휴지통 항목은 목록·카테고리 개수·대표 태그·최신 썸네일·관심사 집계에서 빠지고, 되돌리면 원래 위치(`taken_at` 최신순)로 돌아온다. 휴지통 항목의 카테고리는 수정할 수 없다. **서버와 기기 사진은 건드리지 않는다.**
- **3주차 이후 범위(미정, 제안만)**: ① 실제 **기기 사진 삭제 또는 시스템 휴지통 이동**(안드로이드는 `MediaStore` 휴지통 API/삭제 권한 확인이 필요, 사용자 확인 절차 설계) ② **서버 삭제 API**(예: `DELETE /api/screenshots/{id}` 또는 휴지통 상태 동기화 — 서버에 이미 저장된 OCR 텍스트·카테고리·태그·요약을 어떻게 지울지, 휴지통 보관 기간) ③ 휴지통 화면(목록·비우기·복원). MVP 범위 밖이라 구현하지 않고 제안으로만 둔다.
- 개인정보: 휴지통으로 옮기는 것은 서버 전송과 무관하다. 서버 삭제가 생기면 "저장하는 항목(OCR 텍스트·카테고리·태그·요약)"의 삭제 방식을 처리방침에 명시한다.

## 7. 아키텍처

```
[Flutter 앱]
  ├─ 앨범에서 스크린샷 읽기 (photo_manager)
  ├─ 기기 내 OCR (ML Kit)
  ├─ 기기 내 민감 정보 필터 · 앱 기반 분류
  │    강한 민감 정보(→ ETC), 은행·증권(→ ETC), 메신저(→ CHAT) 캡처는 기기에서 직접 분류,
  │    텍스트·이미지 모두 기기를 떠나지 않음 / 전화번호는 [전화번호]로 가린 뒤 텍스트만 전송
  ├─ OCR 글자 수 ≥ 기준값 → 텍스트 + 메타데이터만 전송
  │  OCR 글자 수 < 기준값 → (이미지 분석 동의 시) 긴 변 1024px 축소 이미지를 함께 전송
  ├─ 원본 이미지는 기기에만 보관     ← 서버로 가는 것은 분석용 축소본뿐
  └─ 정리 UI / 카테고리 수정 / FCM 푸시 수신

[Spring Boot 서버]
  ├─ 분석 API: 텍스트(+ 축소 이미지) → LLM → 카테고리·태그·요약 저장
  │            이미지는 메모리에서 LLM으로 전달만 하고 저장·로그하지 않음
  ├─ 관심사 집계 스케줄러 (주 1회)
  └─ FCM 푸시 발송

[DB]
  └─ device / screenshot / tag / screenshot_tag / interest_alert
```

### 개인정보 원칙
> **민감한 캡처는 기기를 떠나지 않고, 분석용 이미지는 동의한 경우에만 보내며 서버에 저장하지 않는다.**

- 서버가 저장하는 것은 OCR 텍스트, 카테고리, 태그, 요약, 메타데이터뿐이다. **이미지는 저장하지 않는다.**
- 원본 이미지는 기기에만 있고, 서버로 가는 이미지는 분석용으로 줄인 축소본(긴 변 1024px)이다.

### 안전장치
| 장치 | 내용 |
|---|---|
| 기기 내 민감 정보 필터 (2단계) | ① **강한 민감 정보**(주민등록번호, 카드·계좌번호, 인증번호(OTP), 비밀번호) 패턴이 OCR 텍스트에 보이면 **서버로 보내지 않고 기기에서 `ETC`로 분류**한다. 텍스트·이미지 모두 기기를 떠나지 않으며, 정리 화면에서 기본 숨김이고 "분석 제외" 필터에서 모아 본다. ② **전화번호**는 차단하지 않고 OCR 텍스트에서 `[전화번호]`로 **가린 뒤 텍스트만** 보낸다(이미지는 번호가 그대로 있으므로 보내지 않음). **앱 마스킹 + 서버 재확인**: 앱 실수로 이미지가 함께 와도, OCR에 `[전화번호]` 표시가 있으면 서버는 이미지를 쓰지 않고 무시한다(표시 문자열은 서버 코드 상수 한 곳). 한계: 서버는 표시만 재확인하며, 마스킹되지 않은 전화번호를 스스로 찾아내지는 않는다. 가게 전화번호가 많은 `PLACE` 캡처가 통째로 빠지지 않게 하기 위함이다. 패턴 목록과 마스킹 규칙은 구현 단계에서 정한다. |
| 앱 기반 기기 내 분류 | **은행·증권·메신저 앱에서 찍은 캡처**는 "분석에서 제외"하지 않고 **서버로 보내지 않은 채 기기에서 바로 분류**한다. 메신저 앱 → `CHAT`(일반 캡처처럼 노출), 은행·증권 앱 → `ETC`(기본 숨김, "분석 제외" 필터에서 조회). 그래서 `CHAT` 카테고리는 유지되고 **대화 내용은 기기 밖으로 나가지 않는다**. 앱은 **갤럭시 스크린샷 파일명의 앱 이름**으로 판별한다(예: `Screenshot_날짜_시간_앱이름.jpg`). 앱 이름 목록은 구현 단계에서 정한다. **Remine 앱 자신의 스크린샷**(파일명 앱 이름이 `Remine`, 대소문자·공백 무관)은 분류 대상이 아니라서 OCR·전송을 하지 않고 목록에도 올리지 않는다. |
| 이미지 분석 동의 (끄기 가능) | 첫 실행 때 이미지가 분석을 위해 전송됨을 알리고 동의를 받는다. 설정에서 언제든 끌 수 있고, 끄면 이미지 없이 텍스트만 보낸다. |
| 이미지 저장·로그 없음 | 서버는 수신한 이미지를 디스크·DB·객체 저장소에 쓰지 않는다. 요청·오류 로그에도 이미지(base64 포함)를 남기지 않는다. 구현: ① multipart 업로드를 **메모리에서만** 처리(`file-size-threshold`를 상한보다 크게 — Spring 기본값 0B는 모든 파트를 임시 파일로 씀), ② 디코딩·재인코딩은 ImageIO **메모리 스트림**만 사용(디스크 캐시 없음), ③ 재인코딩으로 EXIF·GPS 제거, ④ 이미지 바이트는 요청 처리 중 지역 변수에만 있고 엔티티·캐시·필드에 두지 않음, ⑤ 이미지 관련 로그·예외는 건수·바이트 수·사유 코드뿐(고정 문구), ⑥ 장당 1MB·요청 전체 12MB·픽셀 수 25,000,000 상한(압축폭탄 방어). 임시 파일·로그·DB 흔적 없음은 실제 Tomcat 통합 테스트로 검증한다. |
| 다른 사용자 운영은 유료 등급 | LLM 제공사의 무료 티어는 입력이 제품 개선에 쓰일 수 있다. 다른 사용자의 캡처를 받는 운영은 유료 등급(입력이 학습에 쓰이지 않는 조건)만 사용한다. 지금 배포처럼 본인 캡처만 보내는 동안은 이를 알고 무료 티어를 쓴다. "다른 사용자에게 열기"에는 **APK 공개 배포도 포함**된다. 그래서 지금은 GitHub Releases 등에 APK를 공개하지 않고(시연 영상·README로 대체), 공개 전에 유료 등급 전환 또는 초대한 기기만 받도록 제한한다. |
| 처리방침 고지 | 이미지 전송 여부, 제3자(LLM 제공사) 처리, 저장하지 않는 항목, 동의 철회 방법을 개인정보 처리방침에 명시한다. |

### 운영 DB 전환 (PostgreSQL, Flyway V1)
- H2 인메모리에서 PostgreSQL로 옮기면서 스키마를 `V1__init.sql` 하나로 시작했다. H2에는 남은 데이터가 없어(인메모리) **백필·태그 병합은 하지 않았다.** V1이 처음부터 최종 형태다:
  - `screenshot.auto_category`·`category_source` 포함, enum 컬럼(category·auto_category·category_source, interest_alert.category·status)에 CHECK
  - `tag.normalized_name` unique(`#`·공백·대소문자 무시한 키), `tag.name`은 unique 아님
  - FK 인덱스: PostgreSQL은 자동으로 만들지 않아 `screenshot_tag(tag_id)`를 추가했다(screenshot_id 쪽은 unique가 맡음)
- 수정 이력은 저장하지 않는다(현재 값과 최초 AI 값만). 여러 번 고친 중간 값은 남지 않는다.
- 스키마 변경은 새 `V{n}__*.sql`로만 한다. 적용된 파일은 고치지 않는다.
- 시각은 `timestamp`(시간대 없음)이고 기준은 Asia/Seoul이다(서버가 JVM 기본값·Clock·Hibernate JDBC 시간대를 고정). 배포 서버가 UTC여도 같다.
- ID는 SEQUENCE(50개씩 할당)라 analyze 저장의 INSERT가 배치된다. 300장 기준 실행 SQL 916 → 29회(`ScreenshotAnalyzeQueryCountTest`).

### 실사용 정확도 측정 (F-05)
- 분석된 캡처 = `analyzed_at`이 있는 행. `corrected` = `USER` 이면서 `category ≠ auto_category`, `confirmed` = `USER` 이면서 `category = auto_category`, `unreviewed` = `AUTO`.
- **수정률** = corrected / 분석된 캡처 수.
- **정확도 상한** = 1 − 수정률. 안 고친 캡처가 맞는지는 알 수 없고(틀려도 못 보거나 안 고칠 수 있음) 정확도 자체가 아니라 **상한**이다.
- **검토 기준 정확도** = confirmed / (confirmed + corrected). 사용자가 직접 본 표본뿐이라 작고 편향될 수 있어 참고용이다.
- **혼동 쌍** (auto_category → category) 건수: 프롬프트·카테고리 정의 개선의 입력.
- 한계: 수정 이력 없음, 기기 안에서 분류한 캡처(민감·은행·메신저 앱)는 서버에 없어 제외, 모델·프롬프트 버전별 분리는 버전 컬럼(`classifier_version`)이 생기면 가능.
- 조회 API: `GET /api/categories/accuracy` (헤더 `X-Device-Id`) → `{analyzed, corrected, confirmed, unreviewed, correctionRate, accuracyUpperBound, reviewedAccuracy, byAutoCategory:[{category, analyzed, corrected, confirmed}], confusions:[{from, to, count}]}`. 비율은 분모가 0이면 `null`. `confirmed`는 앱 수정 시트의 "응, X 맞아"(같은 값 저장)로 생긴다. `from`/`to` 기간 필터는 아직 없다. `group by auto_category, category, category_source` 쿼리 1회. 기기 전체 합산은 인증이 없는 지금은 API로 열지 않고 관리용 SQL로만 본다.

**analyze multipart 형식**: `request` 파트(텍스트, 위 JSON 본문과 같은 스키마) + 이미지 파트 `image.<localAssetId>`(JPEG, 캡처당 최대 1개, 이미지는 동의한 경우의 짧은 OCR 캡처에만). 이미지는 저장·로그하지 않는다.

| 상황 | 응답 |
|---|---|
| 이미지가 JPEG가 아니거나 읽을 수 없음, 픽셀 수 초과 | 200, 그 캡처만 `failed` `IMAGE_INVALID` |

| 파트 하나 5MB 또는 요청 전체 12MB(`maxRequestBytes`) 초과 | 413, 요청 전체 거절 |
| `request` 파트 없음·JSON 오류·필드 오류, 요청에 없는 `localAssetId`의 이미지 파트, 같은 이름 파트 중복, `image.` 이외 이름의 파일 파트 | 400, 분류 시작 전 요청 전체 거절(메시지에 요청 내용 없음) |

**앱 재전송 규칙** (`failed.reason`별):

| reason | 앱이 할 일 |
|---|---|
| `IMAGE_TOO_LARGE` | 이미지를 **더 줄여서**(긴 변·JPEG 품질) 재전송. `/api/config`의 `imageMaxBytes`를 지킨다 |
| `IMAGE_INVALID` | **이미지 없이** 재전송. 같은 이미지를 반복 전송하지 않는다 |
| `LLM_CALL_FAILED` / `LLM_INVALID_RESPONSE` | 같은 요청을 나중에 다시 전송 |
| `IN_PROGRESS` | 같은 기기의 앞선 요청이 그 캡처를 분석 중(앱 타임아웃 뒤 재전송 등). 실패로 세지 않고 이번 실행에서 빼며, 다음 실행에서 다시 보낸다(그때 끝나 있으면 `skipped`) |
| `DEADLINE_EXCEEDED` | 요청 마감(`remine.analyze.deadline`, 4분 — 앱 타임아웃 5분보다 짧게)이 지나 서버가 분류를 시작하지 않음. `IN_PROGRESS`와 같이 처리 |

## 11. 리스크

- **분류 정확도**: 스크린샷은 텍스트가 섞여 있어 LLM이 헷갈리기 쉽다 → 1~2주차에 실제 스크린샷 50장으로 프롬프트 검증.
- **LLM 비용**: 첫 실행 시 대량 분석 → 배치 처리 + 최근 N장 제한. 이미지를 쓰면 장당 비용이 약 2.4배(실험 기준 $0.24 → $0.58 / 1,000장)이므로 짧은 캡처에만 쓰는 하이브리드로 완화.
- **분석 지연**: 분류는 순차 호출이고(무료 등급 RPM 15 기준 호출 간격 4.5초) 서버는 LLM 호출 중 DB 트랜잭션을 쥐지 않는다. 그래도 요청 하나가 길어지므로 최대 20장으로 제한하고, 더 빠르게 하려면 비동기·병렬화가 필요하다.
- **글자 없는 스크린샷**: OCR 텍스트가 없는 캡처는 이미지 분석에 동의한 경우 이미지로 분류하고, 동의하지 않았으면 `기타`로 분류 (MVP 한계로 명시).
- **개인정보**: 분석용 이미지가 제3자(LLM 제공사)로 전송된다. 민감 정보 필터, 동의(끄기 가능), 저장·로그 없음, 유료 등급, 처리방침 고지로 완화한다.
- **앱 이름 판별의 한계**: 앱 기반 분류는 갤럭시 스크린샷 파일명(`Screenshot_날짜_시간_앱이름`)의 앱 이름에 의존한다.
  다른 제조사는 파일명 규칙이 다르고, 언어 설정에 따라 앱 이름이 달라지며(한글/영문), 앱 이름이 바뀔 수도 있어 판별이 빗나갈 수 있다.
  빗나가면 은행·메신저 앱 캡처가 일반 경로로 전송될 수 있으므로 OCR 패턴 필터(강한 민감 정보)를 이중 방어로 둔다. 갤럭시 외 기기는 MVP에서 판별을 보장하지 않는다.
- **기기 내 분류 캡처는 서버 집계·관심사 알림에 반영되지 않는다 (의도된 동작)**: 개인정보 보호를 위해 이 캡처들은 서버로 가지 않으므로
  `/api/categories/summary`와 관심사 알림(F-04)에 포함되지 않고, 앱이 기기에서 보관·합산한다. 사용자 카테고리 수정(F-05)도 이 캡처는 기기에만 저장된다.
- **전화번호가 있는 캡처는 텍스트만으로 분류된다**: 이미지를 보내지 않으므로 OCR이 짧아도 하이브리드의 이미지 경로를 쓰지 못해 정확도가 낮을 수 있다.
- **하이브리드 기준값의 일반화**: 150자는 43장·Tesseract OCR로 고른 값이다. ML Kit OCR과 더 큰 표본으로 재검증하기 전까지 설정값으로 두고 고정하지 않는다.
- **무료 한도**: 일반 `gemini-3.8-flash`는 무료 한도가 작아(하루 20회) 개발·검증에는 `gemini-3.5-flash-lite`를 쓴다.
